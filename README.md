# Задание 1

## Уровень 1
В качестве фреймворка для создания микрофронтендов был выбран Webpack Module Federation. Аргументы в пользу данного решения:
- Одним из основных преимуществ Single SPA является возможность объединения микрофронтендов написанных на различных фреймворках. У нас приложение написано только на React, поэтому выигрыша от использования Single SPA в данный момент мы не получим
- Single SPA предоставляет возможности централизованного управления маршрутизацией к микрофронтам и управления жизненным циклом в зависимости от пути. В случае нашего фронта помимо корнего пути определено еще 2: /signup и /signin - поэтому реализовать данное преимущество в текущем виде у нас не получится, а проводить рефакторинг нам не захочется
- Исходя из прошлого пункта для нас будет выигрышнее использовать Webpack Module Federation - его механизм экспорта компонентов хорошо ложится на текущую структуру кода
- В то же время Webpack Module Federation позволяет шарить код и зависимости между микрофронтами (а у нас есть общие компоненты), что позволит избежать дублирование кода, а так же уменьшить размер приложения
- При этом импорт модулей происходит в рантайме, без необходимости рекомпиляции
- Так же как и Single SPA основан на lazy loading, а значит сократится время первоначальной загрузки
- Webpack Module Federation зависит от Webpack, в отличии от Single SPA который не зависит от инструментов сборки, что можно было бы записать в минусы, но в качестве допущения посчитаем, что все разработчики фронта знакомы с данным инструментом

## Уровень 2
- В приложении я вижу 2 основных функциональных блока - профиль пользователя и карточки. Каждый из этих блоков - отдельная бизнес-область, поэтому они являются отличными кандидатами на выделение в микрофронты
- Все что связано с аутентификацией так же хочется выделить в свой модуль тк это отдельная область со своей спецификой, пускай она немного и пересекается с профилем пользователя
- Нужен модуль для общего кода. Лично мне немного дико выделять для этого целый микрофронтенд (особенно если как бекендщику провести аналогию с мс), но одно из преимуществ Module Federation - это шаринг общего кода, а интернет говорит, что делать это через микрофронт не запрещается

В итоге получаем следующее разделение по микрофронтам:
- auth - содержит логику по регистации, логину, логауту и тп
- cards - содержит логику по работе с карточками
- commons - для различных общих зависимостей 
- host - базовое приложение
- users - содержит логику для работы с пользователем

  Структура папок для микрофронтов практически не отличается от той, что была до разделения на микрофронты. За одним лишь исключением - blocks переименован в styles, такое название кажется более логичным для .css файлов.

Микрофронты положил в папку microfrontend по большей части ради удобства, чтобы было наглядно видно, какие файлы в них не попали. А так не вижу в этом особого смысла, если на уровне папки frontend не появится чего-то отличного, от микрофронтов (библиотеки или может еще что-то)

Для каждого микрофронта описана структура + краткий перечень действий, которые выходили за рамки простого переноса файликов, а так же мои мысли по поводу происходящего.

Рефакторинг чтобы оно все заработало не проводился, код переносился как есть, просто хотелось по-максимуму разнести логику по соответствующим микрофронтам. В коде постарался оставить соответствующие комментарии.

### Микрофронтенд auth
```
/frontend/microfrontend/auth
  /src
    /components
      Login.js // компонент для формы аутентификации
      ProtectedRoute.js // компонент который дает доступ к другим компонентам если пользователь залогинен, иначе редирект на логин
      Register.js // компонент для формы регистрации
      SignOut.js // компонент для обработки логаута
    /styles
      /auth-form
        ... стили для формы, которая используется в компонентах Login.js и Register.js
      /login
        login.css // стили для компонента входа
    /utils
      api.js // для вызовов апи методов регистрации и логина
```
- в компонент Login.js перенесена функция onLogin из App.js (как есть, без рефакторинга чтобы оно все работало)
- в компонент Register.js перенесена функция onRegister из App.js (как есть, без рефакторинга чтобы оно все работало)
- выделен компонент SignOut.js в который помещена функция onSignOut из App.js как есть
- auth.js переименован в api.js
